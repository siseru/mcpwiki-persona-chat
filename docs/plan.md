# 計画書: MCPWiki「生きたグレイホーク市」拡張 (Living City)

リポジトリ名は仮称（`mcpwiki-persona-chat`、ローカルは `/home/ubuntu/persona-chat/`）。

## 課題

MCPWiki の記事（宿屋、店、施設、組織）を、LLM が演じる NPC と会話できる場にする。

- NPC は人格と記憶を持ち、PC との会話を覚えている。
- 複数人が同時に話せる施設と、定員1の施設がある。
- 仕組みは MCPWiki 本体から分離し、新しいリポジトリで作る。既定では OFF で、OFF の間は本体にも AWS にも拡張のリソースがない。

MCPWiki は D&D 専用ではなく、Markdown で書けて MCP 連携できる軽量な Wiki である。技術ナレッジの蓄積など別の用途も想定されるため、本体は汎用のまま保つ。

## 要件（確定事項）

- リポジトリ: 新しい GitHub リポジトリを `siseru/` 配下に作る（仮称 `mcpwiki-persona-chat`、ローカルは `/home/ubuntu/persona-chat/`）。名前は汎用。NPC、人格、記憶、部屋の仕組みを汎用に作り、グレイホーク固有の内容は記事側に置く。
- 配備: MCPWiki と同じ AWS アカウントとリージョン（us-west-2）に、別の CDK スタックとして配備する。配備時に着脱でき、OFF なら何も作らず何も配らない。
- ガード: 新リポジトリが専用のガードスタックを持つ。本体の `DEV_SERVICES` は触らない。
- LLM: Amazon Bedrock。
- 記憶: AgentCore Memory のみ採用する。Runtime、Gateway、Policy、Identity は使わない。Observability は本文を含めない計測に限る。
- 記憶の鍵: 「NPC × PC 記事」。PC は Wiki 記事（type: PC）で、ユーザーが所有する。
- DM 機能（初版）: 観戦、記憶の編集と撤回、NPC の乗っ取り、世界イベントの登録、NPC 下書き支援。
- NPC の配置: どの店・組織に NPC を置くかは管理者（DM）が手動で決める。下書き支援は、DM が選んだ記事から LLM が案を作り、DM が直して採用する。自動での配置はしない。
- 世界イベント: DM の手動登録と期間による失効まで。暦（世界内の日時）も DM が手動で進める。自動進行と NPC 同士の噂の伝播は対象外。
- 原則: LLM は台詞だけを書く。事実、状態、権限、秘密の開示条件はサーバーが決める。
- MCPWiki の流儀を新リポジトリにも写して守る:
  - 本文やトークンをログに出さない。
  - web で `innerHTML` と `localStorage` を使わない。
  - MCP に削除ツールを置かない。
  - lint、cdk-nag、依存の許可リストに通す。

## 背景（調べた事実）

- `ArticleMeta.type` は自由文字列で、`extra`（OKF 拡張キー）は保持される。施設、NPC、PC は type と extra で表せ、本体の型追加は不要。
  - REST の POST と PUT は `extra` を受け付ける。更新で `extra` を省くと、今の値が残る。OKF のインポートも `extra` を通す。
  - MCP の `create_article` / `update_article` は `extra` を受け付けない。
  - web エディタには `extra` の編集欄がない（保存しても消えはしない）。`extra` は REST か OKF のインポートで書く。
- 記事の取得 API（`GET /api/articles/:id`）は、持ち主の `owner` を返さない（返すのは `ownerName` だけ）。持ち主かどうかは、本人のトークンで `GET /api/articles?mine=1` を呼び、その結果に含まれるかで確かめられる。
- Wiki の `status: draft` は OKF の状態で、他の人に見えるかどうかとは関係がない。見える範囲は `readScope` で決まる。
- 本体の構成は CloudFront → HTTP API → Lambda 1本。HTTP API は WebSocket を扱えない。CSP は固定文字列で `script-src 'self'`。SPA（`src/web/app.ts`）にプラグイン機構はない。Lambda の役割に Bedrock、SQS、execute-api の権限はない。
- 本体のガード（`src/infra/guard-stack.ts`）は、dev と prod が同居するアカウントの権限境界（`MCPWikiDevBoundary`、ブートストラップの識別子 `mwdev`）。管理者が手で配備する。`DEV_SERVICES` にないサービスは使えず、名前が `MCPWiki-dev*` でないスタックとそのリソースは拒否される。そのため、新リポジトリのリソースは本体の dev から元々保護されている。
- 認可は本体の `permissions.ts` が唯一の源。拡張は Wiki の内部コードを取り込まず、HTTP API だけで話す。
- AgentCore Memory には CloudFormation リソース（`AWS::BedrockAgentCore::Memory`）があり、us-west-2 で使える。費用は公開例（短期イベント10万件、長期レコード1万件、検索2万回）で月 約19ドル。
- Bedrock の Anthropic モデルは、アカウントで 1 回、利用目的の申請が要る。us-west-2 では、クロスリージョン推論（`us.` の推論プロファイル）でしか呼べないモデルがある。その場合、IAM とガードには、推論プロファイルと、複数リージョンの基盤モデルの ARN の両方の許可が要る。
- Task 2 の検証の結果は [docs/spike.md](spike.md) にある。要点は次のとおり。
  - 記憶の 1 件の撤回、修正、追加はできる。
  - 名前空間のカスタム変数（`{npc}` と `{pc}`）が使える。
  - us-west-2 の Anthropic モデルは、`us.` の推論プロファイルでしか呼べない。
  - S3 と CloudFront の循環は、スタックの間を参照でつながないことで避ける。
  - WebSocket は、短命チケットで認証する。
- まだ確かめていない点: custom 戦略（実行用の IAM ロールが要る）、IAM の条件キーによる名前空間の絞り込み、顧客管理キーでの暗号化。

## 設計

```
[MCPWiki リポジトリ]  汎用の「拡張口」だけを足す(D&D の語は出さない)
  config: extensions: [{id, pathPattern, origin, bundle, connectSrc}] (既定は空)
  有効な拡張ごとに CloudFront の挙動と CSP の connect-src を足す
  SPA が /ext/<id>/ のバンドルを同一オリジンで読み、ホスト API を渡す
  docs/extensions.md に契約(契約バージョン付き)

[新リポジトリ]  拡張の本体(自前の CDK スタックとガードスタック)
  ブラウザ ─ WebSocket ─ API Gateway WebSocket (短命チケットで認証)
                           ├ 入退室 Lambda ─ DynamoDB(拡張専用)
                           ├ SQS FIFO(キュー1つ、MessageGroupId=部屋で直列化)
                           ├ 会話ディレクター Lambda ─ Bedrock
                           │     └ MemoryProvider ─ AgentCore Memory
                           └ DM 管理 / 世界イベント
  Wiki とは HTTP API だけで話す(本体の内部コードは取り込まない)
```

### 層

- L0 拡張口（本体）: `extensions` 設定、CloudFront と CSP の条件付き追加、SPA のマウントとホスト API、契約バージョン。
- L1 接続: API Gateway WebSocket。トークンは URL に載せず、短命チケット（または接続後の最初のメッセージ）で認証する。Cognito JWT は、本体の `auth.ts` と同じ規則で検証する（`token_use=access`、client_id、`aws.cognito.signin.user.admin` スコープの拒否）。接続の最大時間を決め、一定の時間ごとにチケットを取り直させる（API Gateway の上限は 2 時間、無操作の切断は 10 分）。会話中は Wiki を読まないため、無効にされた利用者の接続が残り続けないようにするためである。
- L2 施設と在室: 定員、排他（DynamoDB の条件付き書き込み）、入退室、営業時間。
- L3 会話ディレクター: SQS FIFO（キューは 1 つ、MessageGroupId を部屋にする）で、部屋ごとに発言を直列化。宛先と返信の要否を判定し（宛先があるか、しばらく静かな場合に返し、返信の連鎖を防ぐ）、返答を在室者全員に流す。
- L4 人格・記憶・状態: 人格の正本は管理者用の Wiki 記事（type: NPC、秘密を含むため `readScope: admin`）。会話に出すかどうかは Wiki の `status` ではなく、DM が拡張の画面で公開したときに取るスナップショットで決める。記憶は `MemoryProvider` の口の裏（AgentCore 実装とメモリ内実装）。秘密は段階開示（条件を満たしたときだけサーバーがプロンプトに入れる）。
- L5 LLM ゲートウェイ: Bedrock。利用者、部屋、NPC ごとの予算とレート制限、出力検査、プロバイダの差し替え可能性、任意で Bedrock Guardrails。
- L6 DM 管理: 観戦、記憶の編集と撤回（web 管理のみ）、NPC の停止と乗っ取り、世界イベント、暦の進行、費用表示、緊急停止。

### Wiki 記事の読み方

- NPC の人格記事の公開（スナップショット）は、DM が拡張の画面から実行する。拡張は DM 本人のトークンで記事を読む。
- 入室時の「この PC 記事は本人のものか」の確認は、本人のトークンで `GET /api/articles?mine=1` を呼び、その記事が含まれるかで確かめる（記事の取得 API は `owner` を返さないため）。
- 会話中は Wiki を読まない。
- トークンはその1回の呼び出しにだけ使い、保存もログ出力もしない。
- コアに機械用クライアントや新しい権限は足さない。

### 契約

取り決めるのは、config の `extensions` の形、ホスト API（トークン取得、いま開いている記事、描画先の DOM）、契約バージョンの3つだけ。拡張は起動時にバージョンを照合し、合わなければ「非対応」と表示して止まる。

拡張のバンドルは Wiki と同じオリジンで動き、利用者（管理者を含む）のトークンを読める。そのため、拡張のパイプラインが侵害されると本体の prod も侵害される。これを防ぐため、`extensions` の各項目にバンドルの SRI ハッシュ（`integrity`）を持たせ、SPA は一致したバンドルだけを読み込む。新しい版のバンドルは、本体の設定のハッシュを更新し、本体の承認（prod は 2 回）を経て初めて使われる。

拡張の接続先（WebSocket の execute-api のドメイン、バンドル用バケットのドメイン）は環境ごとの値なので、本体の規則どおり GitHub の vars ではなくシークレットに入れる。CI の `mask.sh` と `redact.mjs` の対象に加え、デプロイ後にはログ全体を点検する。

### データの寿命

| 出来事 | 記憶（AgentCore Memory） | 会話ログ |
|---|---|---|
| PC 記事の削除 | その PC の名前空間を消す | その PC の分を消す |
| 利用者の無効化 | 残す（再有効化に備える）。DM に一覧で知らせる | TTL で消える |
| NPC 記事の削除 | DM の確認後、その NPC の名前空間を消す | その NPC の分を消す |

本体からの通知の口はないため、拡張は DM の画面を開いたときと定期の点検で、本人のトークンではなく DM のトークンで記事の存在を確かめ、該当があれば DM に処理を促す。消す操作は DM が実行し、監査ログに残す（本文は残さない）。

### 世界イベント（最小モデル）

- 範囲（街、地区、施設、NPC）、期間（世界内の日時）、公開度（公開、噂、DM のみ）、効果（プロンプトへの文脈、施設状態、NPC の在不在）。
- 期間が過ぎたら自動で失効する。失効後に NPC の記憶へ残すかどうかは、イベントごとに指定できる。

### Task 7: NPC 下書き支援

- 目的: DM が記事から NPC の人格案を作り、確認して採用できるようにする。
- 内容:
  - 拡張の DM 画面に「この記事から NPC の下書きを作る」を追加する。
  - DM 本人のトークンで記事を読み、Bedrock に渡して構造化された下書きを作る。内容は、名前、役割、人格、口調、知っていること、秘密と開示条件の候補、挨拶。
  - 記事本文は信頼しないデータとして囲んでから渡す。出力はスキーマで検証する。
  - 各項目に「記事のどの部分に基づくか」を付ける。記事にない設定は「補った設定」と区別して表示する。
  - 秘密の候補は、既定で「未開示」にする。
  - 画面で DM が編集し、「採用」を押したときだけ、DM 本人のトークンで Wiki に type: NPC の記事を `readScope: admin`、`status: draft` で作る。会話には自動では出さない。会話に出すのは Task 6 の公開の手順で DM が行う。
  - 生成は DM ごとの予算の対象にする。
- テスト:
  - フェイクのプロバイダで、出力が崩れた場合、スキーマ違反の場合、記事本文に指示文が含まれる場合の挙動を確認する。
  - 「補った設定」が出典つきの設定と区別されること。
  - 採用するまで Wiki に何も書かれないこと。
  - viewer と editor でも作成・公開の権限が本体の規則どおりであること。
- Demo: DM が公式記事の「グリーンドラゴン亭」を選んで下書きを作り、直して採用すると、NPC 記事（下書き）ができる。公開すると会話の場に出る。

### Task 8: 1:1 の NPC 会話（Bedrock、記憶なし）

- 目的: PC が NPC と話せる、最初の動く縦の機能を作る。
- 内容:
  - 入室の API を作る。入室時に PC 記事の所有を、本人のトークンで `GET /api/articles?mine=1` を呼んで確認する。
  - メッセージ送信、Bedrock 呼び出し（プロバイダの口の裏）、返答の逐次配信を作る。
  - 会話ログは拡張の表に置き、TTL を付ける。
  - 利用者ごとの予算とレート制限を入れる。
  - 拡張の画面に「入る」ボタンと会話欄を作る。
- テスト: プロバイダをフェイクにして会話の流れを確認する。他人の PC 記事では入れないこと、予算超過の拒否、本文がログに出ないこと。
- Demo: 宿屋のページで PC を選んで入り、リカードと会話できる。

### Task 9: MemoryProvider と AgentCore Memory の接続

- 目的: NPC が PC との会話を覚えるようにする。
- 内容:
  - `MemoryProvider` の口を作る。実装は AgentCore 用とメモリ内の2つ。
  - 拡張スタックに `AWS::BedrockAgentCore::Memory`（暗号化キー、保存期間、抽出戦略）を追加する。
  - 抽出の指示文を「NPC の視点で覚える」ものに差し替える（custom 戦略。先に実行用ロールで確かめる。だめなら組み込みの戦略のまま、注入の前に「ユーザー = この PC」と読み替える）。
  - 世界内の日時は、イベントの本文に明示する（抽出は現実の日付で考えるため）。
  - 会話の終了時に記憶を取り込み、次回の会話前に検索して注入する。
  - 鍵は「NPC × PC 記事」。カスタム変数で `/npc/{npc}/pc/{pc}/` とし、値は記事 ID を正規表現で検証する。会話中は、その組の `namespace` だけを検索する（`namespacePath` は DM の画面とデータの寿命の処理だけで使う）。
  - 撤回は、事実の記憶と要約の記憶の両方を対象にする（要約には、撤回した事実が残るため）。
  - NPC 単位、PC 単位で記憶をまとめて消す操作を、口に含める（「データの寿命」のため）。
- テスト: 契約テストを両実装に通す。別の PC の記憶が混ざらないこと。PC 単位、NPC 単位で消した記憶が、次の検索に出ないこと。
- Demo: ある PC が約束をして退室し、翌日の会話でリカードがその約束に触れる。別の PC には触れない。

### Task 10: 在室管理と複数人の会話

- 目的: 定員、排他、同時会話を実現する。
- 内容:
  - 入退室を DynamoDB の条件付き書き込みで管理する。定員1の施設では、2人目を拒否する。
  - SQS FIFO（キューは 1 つ、MessageGroupId を部屋にする）で、部屋ごとに発言を直列化する。
  - ディレクターが宛先と返信の要否を判定する。
  - 在室者への配信と、切断時の自動退室（TTL とハートビート）を入れる。
- テスト: 同時入室の競合、返信の連鎖が起きないこと、切断後の退室。
- Demo: 3人が同じ酒場に入って話し、NPC が適切に返す。定員1の部屋は2人目が断られる。

### Task 11: DM 管理画面

- 目的: DM が会話を見て、介入し、記憶を直せるようにする。
- 内容:
  - 管理者のみのエンドポイントを作る（web 管理に限る）。
  - 観戦、NPC の停止と乗っ取り（DM の発言を NPC の発言として流す）、記憶の一覧と編集と撤回を入れる。
  - 「データの寿命」の点検を入れる。削除された PC 記事と NPC 記事、無効にされた利用者を一覧にし、DM が記憶と会話ログを消せるようにする。
  - 操作は監査ログに残す（本文は残さない）。
- テスト: 権限の確認（viewer、editor は不可）、監査ログ、撤回した記憶が次回の注入に出ないこと、削除された PC 記事の記憶が点検の一覧に出て、消した後は残らないこと。
- Demo: DM が間違った記憶を撤回し、次の会話に反映されない。

### Task 12: 世界イベントと暦

- 目的: DM が街の出来事を登録し、NPC の振る舞いに反映する。
- 内容:
  - イベントのモデルと失効の処理を作る。
  - 暦を DM の操作で進める（自動進行はしない）。
  - プロンプトへの「今日の出来事」の注入と、施設状態（休業、定員）や NPC の在不在への反映を入れる。
  - 公開度「噂」「DM のみ」の扱いを入れる。DM のみは、開示条件を満たすまで注入しない。
  - 失効後の記憶化を、イベントごとの指定どおりに行う。
  - 管理者用の MCP ツールを足す（削除は置かない）。
- テスト: 期間と失効の境界、公開度ごとの漏えいがないこと、暦を進めたときの開始と失効。
- Demo: DM が「祭り」を登録して暦を進めると、リカードが祭りに触れ、期間が過ぎると触れなくなる。

### Task 13: 費用と安全の仕上げ

- 目的: 運用に耐える保護を入れる。
- 内容:
  - 部屋、NPC、全体の予算と緊急停止を入れる。
  - プロンプトインジェクション対策を入れる。発言を信頼しないデータとして囲む。
  - 出力検査と、任意で Bedrock Guardrails を入れる。
  - 費用の表示を入れる。
- テスト: 注入を試みる発言、予算超過時の動作、緊急停止の動作。
- Demo: 予算を超えると NPC が定型文で返し、DM が緊急停止で全体を止められる。

### Task 14: 配備手順、ドキュメント、OFF の最終確認

- 目的: 有効化と無効化の手順を整え、OFF が本当に空であることを確認する。
- 内容:
  - 両リポジトリに配備手順を書く。順序は、拡張スタックの配備、本体の `extensions` に接続先を書いて再配備、の順。外すときは逆順。
  - 新リポジトリに脅威モデルと対策を書く。拡張のバンドルが Wiki と同じオリジンで動くこと、それを SRI ハッシュと本体の承認で抑えていることを含める。
  - 全体のテストと lint を通す。
- テスト: OFF の配備に拡張のリソースと配信アセットが一切ないことを機械的に確認する。ON と OFF を往復して、Wiki 本体のデータに影響がないことも確認する。
- Demo: 設定1つで拡張を入れ、外せる。外した後は元の Wiki と同じ状態に戻る。

## 進め方の補足
